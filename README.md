# 엑셀 비동기 생성 시스템

> "주문하면 **번호표를 바로 받고**, 주방에선 **요리사 한 명이** 차례대로 만들고, 손님은 **전광판**을 보며 기다린다."

사용자가 엑셀 생성을 요청하면 즉시 응답(작업 번호)을 돌려주고, 백그라운드에서 주문 데이터 10만 건을 엑셀 파일로 만드는 시스템입니다.
위 비유를 실제 구성에 대응하면 아래와 같고, 이후 본문에서는 실제 용어(작업·워커·대기열)를 사용합니다.

| 비유 | 실제 구성 |
|---|---|
| 번호표를 바로 받음 | `POST /api/jobs` → 즉시 `202 Accepted` + job_id |
| 주문판 | DB `jobs` 테이블 (= 작업 대기열) |
| 요리사 1명 | 백그라운드 워커 스레드 1개 — 엑셀 생성은 한 번에 하나씩 |
| 전광판 | 프론트엔드가 2초마다 상태 조회 (진행 중인 작업이 있을 때만) |

---

## 1. 실행 방법

```bash
docker compose up --build
```

- 접속: http://localhost:8000
- 첫 실행 시 PostgreSQL이 뜨면서 주문 더미 데이터 10만 건이 자동으로 들어갑니다.
- 외부 계정이나 외부 서비스 없이 로컬에서만 동작합니다.
- 처음부터 다시 시작하려면(DB·파일 초기화): `docker compose down -v`


### API

| Method | Path | 설명 |
|---|---|---|
| `POST` | `/api/jobs` | 엑셀 생성 요청. 파일은 만들지 않고 작업만 등록한 뒤 **즉시 202** 반환 (대기 20건 이상이면 429) |
| `GET` | `/api/jobs` | 요청 목록 (최신순) |
| `GET` | `/api/jobs/{id}` | 단건 상태 조회 |
| `GET` | `/api/jobs/{id}/download` | 완료된 파일 다운로드 (`done`이 아니면 409) |

## 2. 기술 스택과 선택 이유

| 영역 | 선택 | 이유 |
|---|---|---|
| 백엔드 | **FastAPI** | 평소 Python을 주로 써서 코드를 자신 있게 설명할 수 있음 |
| 비동기 처리 | **워커 스레드 1개 + DB 테이블 대기열** | 아래 "설계 시 고민한 점" 참고 |
| DB | **PostgreSQL** | 서버 사이드 커서로 대용량을 나눠 읽을 수 있고, `FOR UPDATE SKIP LOCKED`로 테이블을 대기열처럼 쓰기 좋음. SQLite는 쓰기 잠금이 DB 파일 단위라 API와 워커가 동시에 쓰는 구조에 불리함 |
| DB 드라이버 | **psycopg 3** (ORM 없이 SQL 직접 작성) | 어떤 쿼리가 실행되는지 코드에서 바로 보이게 하려고. 테이블 2개짜리 과제라 ORM의 이점이 적음 |
| 엑셀 | **XlsxWriter** (`constant_memory` 모드) | 이미 쓴 행을 메모리에 계속 들고 있지 않고 임시 파일로 내보냄 |
| 프론트엔드 | **순수 HTML + JS** | 화면이 표 하나와 버튼 하나라 빌드 도구가 필요 없음. FastAPI가 같이 서빙해서 구성이 단순함 |
| 상태 확인 | **폴링 (2초)** | 가장 단순하고 디버깅이 쉬움. 진행 중인 작업이 있을 때만 폴링하고, 끝나면 멈춤 |

## 3. 설계 시 고민한 점

> 전제: **단일 프로세스 · 단일 워커**로 설계했습니다. (과제의 "백엔드 컨테이너 1개, 스케일아웃 불가" 제약에 맞춤)
> 서버 시작 시 정리 코드(3-4)와 대기열 상한 잠금(3-5)이 이 전제에 의존합니다.

### 3-1. 요청과 처리를 분리하고, 엑셀 생성은 한 번에 하나만
FastAPI `BackgroundTasks`는 요청이 들어올 때마다 작업을 바로 시작합니다. 동시 작업 수가 늘면 제한된 CPU(0.5)와 메모리(512M)를 나눠 쓰게 되어 **메모리와 CPU 부담이 커질 수 있고**, 작업 상태가 프로세스 메모리에만 있으면 서버 종료 시 함께 사라집니다.

그래서 요청 접수와 엑셀 생성을 분리했습니다.
- API는 `jobs` 테이블에 `pending` 행 하나만 넣고 바로 응답합니다.
- 서버 시작 시 워커 스레드 **1개**가 뜨고, 1초마다 가장 오래된 `pending` 작업을 하나씩 가져와 처리합니다.
- **엑셀 생성은 한 번에 하나만 실행해, 생성 작업이 동시에 쓰는 메모리를 제한했습니다.** 대신 요청이 몰리면 뒤 요청의 대기 시간이 늘어납니다. 이 제약에서는 "느리더라도 죽지 않는 것"이 더 중요하다고 판단했습니다.
- uvicorn도 `--workers 1`로 고정했습니다. 프로세스가 늘어나면 워커 스레드도 프로세스마다 생기기 때문입니다.

### 3-2. 별도 메시지 브로커(Celery + Redis 등)를 쓰지 않은 이유
이번 규모(단일 컨테이너, 워커 1개)에서는 **별도 브로커와 워커 운영 구성을 추가하지 않았습니다.** 작업 상태를 어차피 DB에 기록해야 하므로, 이미 있는 PostgreSQL 테이블을 대기열로 쓰면 상태 저장소와 대기열이 한 곳에 있어 구성이 단순합니다.

```sql
-- 워커가 다음 작업을 가져가는 쿼리 (worker.py: claim_next_job)
UPDATE jobs SET status = 'processing', started_at = now()
 WHERE id = (SELECT id FROM jobs WHERE status = 'pending'
              ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED)
RETURNING id;
```
`FOR UPDATE SKIP LOCKED`는 **여러 워커가 동시에 같은 대기 작업을 가져가는 충돌을 막는 쿼리**입니다. 다만 시스템 전체는 단일 워커 전제이므로, 이 쿼리만으로 워커를 늘릴 수 있는 것은 아닙니다. (3-4의 시작 시 정리 로직도 바꿔야 함)

### 3-3. 메모리 — 전체 데이터를 한꺼번에 적재하지 않는다
- **읽기**: `fetchall()`로 10만 건을 한 번에 가져오지 않고, **이름 있는 서버 사이드 커서**(`cursor(name=...)`)로 결과를 DB 쪽에 둔 채 `fetchmany(5000)`으로 **5,000건씩 읽습니다.**
- **쓰기**: XlsxWriter `constant_memory` 모드는 이미 쓴 행을 메모리에 계속 보관하지 않고 임시 파일로 내보냅니다. 대신 **디스크 공간을 쓰고, 이미 쓴 행으로 돌아가 수정할 수 없습니다.** (위에서 아래로 한 번만 쓰는 이 용도에는 문제없음)
- 이렇게 하면 **같은 형태의 데이터에서 전체 행 수가 늘어날 때 메모리가 함께 늘어나는 정도를 줄일 수 있습니다.**

### 3-4. 작업 도중 문제가 생기면 (복구 범위)
| 상황 | 처리 |
|---|---|
| 엑셀 생성 중 오류 | 임시 파일 삭제 → 작업을 `failed`로 기록 (실패 사유 저장) |
| 위 정리 과정에서 또 오류 (예: DB가 계속 죽어 있음) | 예외를 워커 밖으로 던지지 않고 로그만 남김 → **워커는 다음 작업을 계속 처리** |
| 실패 기록까지 실패한 작업 | `processing`으로 남음 → **다음 서버 시작 시** `failed`로 정리 (실행 중 자동 복구는 하지 않음) |
| 서버가 작업 도중 종료됨 | 다음 서버 시작 시 `processing` 작업을 `failed`로 정리하고, 남은 임시 파일을 삭제 |
| 반쯤 만들어진 결과 파일 | `.part` 이름으로 쓰다가 완성 후 `os.replace`로 이름을 바꿔, 완성된 파일만 최종 이름을 가짐 |

- 자동 재시도(`pending`으로 되돌리기)를 하지 않은 이유: **그 작업 때문에 서버가 죽은 것**이라면(예: 메모리 부족) "재시작 → 재시도 → 또 종료"가 반복될 수 있어서, 실패로 남기고 사용자가 다시 요청하게 했습니다.
- 알려진 빈틈: 파일 이름 변경과 DB 완료 기록은 하나의 트랜잭션이 아닙니다. 이름 변경 후 DB 기록이 실패하면 **완성된 파일은 남지만 작업은 완료로 기록되지 않을 수 있습니다.**

### 3-5. 그 밖의 작은 결정들
- **대기열 상한 (20개)**: `pending`이 20개 이상이면 `429 Too Many Requests`를 반환합니다. "개수 확인 → 등록" 사이에 다른 요청이 끼어들면 상한을 넘을 수 있어서, 이 구간을 **잠금(`threading.Lock`)으로 한 번에 한 요청씩만** 실행합니다. (단일 프로세스 전제라 파이썬 잠금으로 충분)
- **DB 연결 두 개**: 주문 데이터를 일관되게 읽는 연결(한 트랜잭션)과 진행률을 즉시 저장하는 연결(autocommit)을 나눴습니다. 같은 연결로 진행률을 갱신하면 읽기 트랜잭션이 끝날 때까지 다른 요청에서 보이지 않기 때문입니다.
- **REPEATABLE READ**: 전체 건수(`count`)를 셀 때와 데이터를 읽을 때 **같은 기준의 데이터**를 보려는 목적입니다. 요청 시점이 아니라 **워커가 처리를 시작한 시점의 스냅샷**입니다.
- **시드 데이터**: 파이썬에서 10만 번 INSERT하는 대신 Postgres `generate_series`로 SQL 한 번에 생성합니다. (`db/init/02_seed.sql`)
- **헬스체크**: `pg_isready -h 127.0.0.1`로 검사합니다. Postgres 이미지는 init 스크립트(시드)를 실행하는 동안 TCP 접속을 받지 않으므로, 시드가 끝난 뒤에 앱이 시작됩니다.

## 4. DB 설계

```
orders (과제 스키마 그대로)                jobs (엑셀 생성 작업 = 대기열)
─────────────────────────                ─────────────────────────────
id            SERIAL PK                  id              SERIAL PK
user_name     VARCHAR                    status          pending/processing/done/failed (CHECK 제약)
product_name  VARCHAR                    requested_at    요청일시 (DEFAULT now())
category      VARCHAR                    started_at      워커가 가져간 시각
amount        INTEGER                    finished_at     완료/실패 시각
status        VARCHAR                    file_path       완성된 파일 경로
order_date    TIMESTAMP                  total_rows      전체 행 수
                                         processed_rows  지금까지 쓴 행 수 (진행률)
                                         error_message   실패 사유
                                         INDEX (status, id)  ← "가장 오래된 pending" 조회용
```

`docker compose up --build`로 띄운 환경(앱 컨테이너 CPU 0.5 / 메모리 512M 제한 적용 확인, Windows + Docker Desktop(WSL2), 호스트 8코어)에서 확인했습니다.
메모리는 `docker stats`를 주기적으로 관측한 값이라, 관측 사이의 순간 최댓값은 놓칠 수 있습니다.

| 항목 | 결과 |
|---|---|
| `POST /api/jobs` 응답 시간 | 약 0.02초 (파일 생성과 무관하게 즉시 202) |
| 10만 건 엑셀 생성 시간 | 약 10~14초 / 건 |
| 생성 중 컨테이너 메모리 (관측) | 약 47~52MiB |
| 결과 파일 크기 | 약 4.2MB |
| 30건 동시 요청 | 21건 접수(202), 9건 거절(429). 접수된 것 중 1건은 곧바로 워커가 가져가 `processing`, **`pending`은 정확히 20건** |
| 생성 중 목록 조회 API 응답 | 평소 약 0.03초 → 생성 중 0.12~0.25초. API와 생성 작업이 같은 프로세스에서 **CPU 자원(0.5)을 공유**해 응답 지연이 늘 수 있습니다 |
| 생성 도중 앱 컨테이너 강제 종료(`docker kill`) | 재시작 시 해당 작업 `failed` 처리, 남은 임시 파일 자동 삭제, 이후 요청 정상 처리 |
| 생성 도중 DB 컨테이너 중지 → 재시작 | 진행 중이던 작업은 실패 기록을 못 해 `processing`으로 남음, **워커는 죽지 않고** DB 복구 후 다음 작업들을 정상 처리. 앱 재시작 시 남은 작업이 `failed`로 정리됨 |

### 확인하다 발견해서 고친 문제
**① 강제 종료 후 25MB 임시 파일이 남음**
처음엔 강제 종료 후 `.part` 파일만 지우면 된다고 생각했는데, 확인해 보니 `.part` 파일은 없고 **컨테이너 `/tmp`에 25MB짜리 파일**이 남아 있었습니다.
XlsxWriter `constant_memory` 모드는 행 데이터를 임시 파일에 먼저 쓰고, 마지막 `close()` 때 압축해서 .xlsx를 만들기 때문입니다. (압축 전 약 25MB → 압축 후 4.2MB)
그래서 임시 파일 위치를 `EXPORT_DIR/tmp`로 고정하고, 서버 시작 시 이 폴더와 `.part` 파일을 비우도록 했습니다. (`worker.py: cleanup_leftover_files`)

**② DB 장애 시 워커 스레드가 종료될 수 있음** (코드 리뷰로 발견)
엑셀 생성 중 DB 오류 → 실패 기록(`_mark_failed`) 시도 → DB가 여전히 죽어 있으면 여기서 또 예외 → 워커 루프가 이 예외를 잡지 않아 **워커 스레드가 종료**되는 문제였습니다. API는 살아서 요청을 받지만 처리할 워커가 없는 상태가 됩니다.
정리 단계(임시 파일 삭제, 실패 기록)의 예외를 각각 처리하고, 워커 루프에서도 작업 단위로 예외를 잡도록 고쳤습니다. 이 상황을 재현하는 테스트 2개는 **수정 전 코드에서 실패하고 수정 후 통과**하는 것을 확인했고, 실제 DB 컨테이너를 중지하는 시나리오로도 확인했습니다. (위 표 마지막 줄)

## 5-1. 비교 실험 — 전체 적재·동시 실행 방식과 나란히 재 보기

같은 DB, 같은 데이터, 같은 리소스 제한(CPU 0.5 / 512M)에서 두 구현을 비교했습니다.

| | 전체 적재·동시 실행 (`experiments/naive`) | 대기열·스트리밍 (이 프로젝트) |
|---|---|---|
| 작업 시작 | 요청마다 `BackgroundTasks`로 바로 실행 (동시 실행 제한 없음) | 대기열에 넣고 워커 1개가 차례로 처리 |
| 데이터 읽기 | `fetchall()`로 한 번에 | 서버 사이드 커서로 5,000건씩 |
| 엑셀 쓰기 | pandas `to_excel()` (openpyxl) | XlsxWriter `constant_memory` |

**측정 조건**: 각 시나리오 1회 실행, 시나리오마다 컨테이너 재시작. 메모리는 `docker stats`를 약 1~2초 간격으로 관측한 최댓값. **성공 = 요청 수 = 접수 수 = 완료 수**일 때만 성공으로 판정합니다.

**결과** (전체 표: `experiments/results.md`)

| 방식 | 요청 | 접수 | 완료 | 결과 | 최대 메모리(관측) | 전체 소요 |
|---|---|---|---|---|---|---|
| 전체 적재·동시 실행 | 1 | 1 | 1 | 성공 | 396MiB | 30.3초 |
| 전체 적재·동시 실행 | 3 | 3 | 0 | **컨테이너 종료 (OOM Killed)** | 512MiB (한도) | - |
| 대기열·스트리밍 | 1 | 1 | 1 | 성공 | 47MiB | 12.2초 |
| 대기열·스트리밍 | 3 | 3 | 3 | 성공 | 48MiB | 35.3초 |
| 대기열·스트리밍 | 5 | 5 | 5 | 성공 | 48MiB | 59.5초 |
| 대기열·스트리밍 | 10 | 10 | 10 | 성공 | 48MiB | 129.9초 |

(대기 상태 메모리: 전체 적재·동시 실행 63MiB, 대기열·스트리밍 38MiB. 이전에 한 번 더 실행했을 때도 같은 결론이었고, 전체 적재 1건의 관측 최댓값은 422MiB로 실행마다 차이가 있었습니다.)

**해석**
- 전체 적재·동시 실행 방식은 1건에서 396MiB(한도의 약 77%)를 썼고, 동시 3건에서 컨테이너가 OOM으로 종료되었습니다. 작업 상태가 프로세스 메모리에만 있어서 종료와 함께 사라졌습니다.
- 이 프로젝트는 동시 요청 1~10건에서 관측 메모리가 거의 같았고, 요청이 늘수록 **전체 소요 시간이 늘어났습니다.** (한 번에 하나씩 처리하므로)
- 두 구현은 **데이터 읽기 방식, 엑셀 라이브러리, 동시 실행 방식을 함께 바꿨기 때문에**, 메모리·속도 차이를 어느 한 기술의 효과로 나눠 말할 수는 없습니다.
- 1회 측정이라 수치에는 오차가 있을 수 있습니다.

재현 방법:
```bash
docker compose -p playstory-exp -f experiments/docker-compose.yml up --build -d
python experiments/run_experiment.py
docker compose -p playstory-exp -f experiments/docker-compose.yml down -v
```

## 6. 한계와 개선 방향 (우선순위 순)

| 순위 | 한계 | 개선 방향 |
|---|---|---|
| 1 | 실패 기록까지 실패한 작업은 서버를 재시작해야 `failed`로 정리됨 | 워커가 주기적으로 "오래된 processing 작업"을 찾아 정리. 파일 이름 변경 후 DB 기록 실패로 남은 파일도 함께 정리 |
| 2 | 만든 엑셀 파일이 계속 쌓임 | 생성 후 일정 기간이 지난 파일과 작업 기록을 정리하는 작업 추가 |
| 3 | 실제 DB와 연결한 API 흐름은 자동 테스트가 없음 (수동 확인만) | 테스트용 DB 컨테이너를 띄워 "요청 → 완료 → 다운로드", "상한 초과 시 429" 통합 테스트 추가 |

그 밖에 알고 있는 제약:
- **단일 프로세스 · 단일 워커 전제**: 인스턴스를 여러 개 띄우면 시작 시 정리 코드가 다른 인스턴스의 작업·파일을 건드릴 수 있고, 대기열 상한 잠금도 프로세스 안에서만 유효합니다.
- **생성 중 API 응답 지연**: API와 엑셀 생성이 같은 프로세스에서 CPU를 공유합니다.
