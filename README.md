# 엑셀 비동기 생성 시스템 🍜

> "주문하면 **번호표를 바로 받고**, 주방에선 **요리사 한 명이** 차례대로 만들고, 손님은 **전광판**을 보며 기다린다."

사용자가 엑셀 생성을 요청하면 즉시 응답(번호표)을 돌려주고, 백그라운드에서 주문 데이터 10만 건을 엑셀 파일로 만드는 시스템입니다.

| 식당 | 이 시스템 |
|---|---|
| 주문하면 번호표를 바로 받음 | `POST /api/jobs` → 즉시 `202 Accepted` + job_id |
| 벽에 붙은 주문판 | DB `jobs` 테이블 (= 작업 대기열) |
| 주방의 요리사 1명 | 백그라운드 워커 스레드 1개 — 엑셀은 한 번에 하나씩 |
| 음식을 한 그릇씩 담아서 냄 | DB에서 5,000건씩 읽어서 바로 파일에 씀 |
| 전광판 | 프론트엔드가 2초마다 상태 조회 (진행 중인 작업이 있을 때만) |

---

## 1. 실행 방법

```bash
docker compose up --build
```

- 접속: http://localhost:8000
- 첫 실행 시 PostgreSQL이 뜨면서 주문 더미 데이터 10만 건이 자동으로 들어갑니다. (1~2초)
- 외부 계정이나 외부 서비스 없이 로컬에서만 동작합니다.
- 처음부터 다시 시작하려면(DB·파일 초기화): `docker compose down -v`

### API

| Method | Path | 설명 |
|---|---|---|
| `POST` | `/api/jobs` | 엑셀 생성 요청. 파일은 만들지 않고 job만 등록한 뒤 **즉시 202** 반환 |
| `GET` | `/api/jobs` | 요청 목록 (최신순) |
| `GET` | `/api/jobs/{id}` | 단건 상태 조회 |
| `GET` | `/api/jobs/{id}/download` | 완료된 파일 다운로드 (`done`이 아니면 409) |

## 2. 기술 스택과 선택 이유

| 영역 | 선택 | 이유 |
|---|---|---|
| 백엔드 | **FastAPI** | 평소 Python을 주로 써서 코드를 자신 있게 설명할 수 있음. 메모리 제한도 512MB로, Spring Boot(1G)보다 가벼운 런타임이 제약 안에서 여유가 있음 |
| 비동기 처리 | **워커 스레드 1개 + DB 테이블 큐** | 아래 "설계 시 고민한 점" 참고 |
| DB | **PostgreSQL** | 서버 사이드 커서로 대용량을 나눠 읽기 좋고, `FOR UPDATE SKIP LOCKED`로 테이블을 큐처럼 쓰기 좋음. SQLite는 쓰기 잠금이 파일 단위라 API와 워커가 동시에 쓰는 구조에 불리함 |
| DB 드라이버 | **psycopg 3** (ORM 없이 SQL 직접 작성) | 어떤 쿼리가 실행되는지 코드에서 바로 보이게 하려고. 테이블 2개짜리 과제라 ORM의 이점이 적음 |
| 엑셀 | **XlsxWriter** (`constant_memory` 모드) | 행을 쓰는 즉시 디스크로 내보내 메모리가 쌓이지 않음. openpyxl보다 쓰기 속도가 빨라 CPU 0.5개 환경에 유리함 |
| 프론트엔드 | **순수 HTML + JS** | 화면이 표 하나와 버튼 하나라 빌드 도구가 필요 없음. FastAPI가 같이 서빙해서 컨테이너도 늘지 않음 |
| 상태 확인 | **폴링 (2초)** | 가장 단순하고 디버깅이 쉬움. 진행 중인 작업이 있을 때만 폴링하고, 끝나면 멈춤 |

## 3. 설계 시 고민한 점

### 3-1. 왜 FastAPI `BackgroundTasks`를 쓰지 않았나 — "요리사를 1명으로 고정"
`BackgroundTasks`는 요청이 들어올 때마다 작업을 바로 시작합니다.
사용자 10명이 동시에 누르면 **엑셀 10개를 동시에 만들게 되고**, CPU 0.5개를 나눠 쓰느라 전부 느려지며 메모리도 10배로 늘어납니다. 서버가 종료되면 진행 중이던 작업이 흔적 없이 사라지는 문제도 있습니다.

그래서 **요청(번호표 발급)과 처리(요리)를 분리**했습니다.
- API는 `jobs` 테이블에 `pending` 행 하나만 넣고 바로 응답합니다.
- 서버 시작 시 워커 스레드 **1개**가 뜨고, 1초마다 가장 오래된 `pending` 작업을 하나씩 꺼내 처리합니다.
- 요청이 100개 몰려도 **메모리 사용량은 "엑셀 1개 만들 때"만큼으로 고정**됩니다. 대신 뒤에 요청한 사람은 기다려야 하는데, 이 제약(단일 컨테이너, 고정 리소스)에서는 "느리지만 죽지 않는 것"이 더 중요하다고 판단했습니다.
- uvicorn도 `--workers 1`로 고정했습니다. 프로세스가 늘어나면 워커 스레드도 같이 늘어나기 때문입니다.

### 3-2. 왜 Celery + Redis를 쓰지 않았나
정석적인 선택지지만 컨테이너 2개(Redis, Celery 워커)가 더 필요하고, 그만큼 메모리도 더 씁니다.
"백엔드 컨테이너 1개" 제약에서 작업 대기열은 **이미 있는 PostgreSQL 테이블**로 충분합니다. 작업 상태를 어차피 DB에 기록해야 하므로, 상태 저장소와 대기열을 한 곳에 두면 둘이 어긋날 일도 없습니다.

```sql
-- 워커가 다음 작업을 가져가는 쿼리 (worker.py: claim_next_job)
UPDATE jobs SET status = 'processing', started_at = now()
 WHERE id = (SELECT id FROM jobs WHERE status = 'pending'
              ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED)
RETURNING id;
```
`FOR UPDATE SKIP LOCKED`는 지금(워커 1개)은 없어도 동작하지만, 나중에 워커를 늘려도 **같은 작업을 두 번 처리하지 않도록** 넣어둔 안전장치입니다.

### 3-3. 메모리 — "10만 건을 한 번에 들지 않는다"
- **읽기**: `fetchall()`로 10만 건을 한 번에 가져오지 않고, **서버 사이드 커서**(`cursor(name=...)`)로 결과를 DB 쪽에 둔 채 `fetchmany(5000)`으로 5,000건씩 가져옵니다.
- **쓰기**: XlsxWriter의 `constant_memory` 모드는 한 행을 다 쓰면 바로 디스크로 내보냅니다.
- 결과적으로 메모리에는 **최대 5,000행만** 올라갑니다. 데이터가 100만 건이 되어도 메모리 사용량은 거의 같고, 시간만 늘어납니다.

### 3-4. 서버가 작업 도중에 죽는다면
- **반쯤 만들어진 파일**: `orders_job_3.xlsx.part`라는 임시 이름으로 쓰다가, 다 쓴 뒤에 `os.replace`로 한 번에 이름을 바꿉니다. 사용자는 완성된 파일만 보게 됩니다.
- **`processing`에 멈춘 작업**: 서버가 켜질 때 `processing` 상태로 남아 있는 작업을 `failed`로 정리합니다.
- **남은 임시 파일**: 서버가 켜질 때 엑셀 라이브러리의 임시 파일과 `.part` 파일을 지웁니다. (아래 "테스트하다 발견해서 고친 문제" 참고)
- 자동 재시도(`pending`으로 되돌리기)를 하지 않은 이유: **그 작업 때문에 서버가 죽은 것**이라면(예: 메모리 부족) "재시작 → 재시도 → 또 죽음"이 무한히 반복될 수 있습니다. 실패로 남기고 사용자가 다시 요청하게 하는 편이 안전하다고 판단했습니다.

### 3-5. 그 밖의 작은 결정들
- **대기열 상한 (20개)**: `pending`이 20개 이상이면 새 요청에 `429 Too Many Requests`를 반환합니다. 번호표가 끝없이 쌓이는 것을 막기 위해서입니다.
- **스냅샷 고정**: 전체 건수(`count`)를 세는 시점과 실제로 읽는 시점 사이에 데이터가 바뀌면 진행률이 어긋날 수 있어서, 읽기 트랜잭션을 `REPEATABLE READ`로 열었습니다.
- **진행률**: 5,000건마다 `processed_rows`를 갱신해 화면에 `%`로 보여줍니다. 진행률 갱신은 데이터를 읽는 트랜잭션과 **다른 연결(autocommit)**로 해야 바로 반영됩니다.
- **시드 데이터**: 파이썬에서 10만 번 INSERT하는 대신 Postgres `generate_series`로 SQL 한 번에 생성합니다. (`db/init/02_seed.sql`)
- **헬스체크**: `pg_isready -h 127.0.0.1`로 검사합니다. Postgres는 init 스크립트(시드)를 실행하는 동안 TCP 접속을 열지 않기 때문에, **시드가 끝난 뒤에 앱이 시작**됩니다.

## 4. DB 설계

```
orders (과제 스키마 그대로)                jobs (작업 = 번호표)
─────────────────────────                ─────────────────────────────
id            SERIAL PK                  id              SERIAL PK
user_name     VARCHAR                    status          pending/processing/done/failed (CHECK 제약)
product_name  VARCHAR                    requested_at    요청일시 (DEFAULT now())
category      VARCHAR                    started_at      워커가 가져간 시각
amount        INTEGER                    finished_at     완료/실패 시각
status        VARCHAR                    file_path       완성된 파일 경로
order_date    TIMESTAMP                  total_rows      전체 행 수
                                         processed_rows  지금까지 쓴 행 수 (진행률)
                                         error_message   실패 사유
                                         INDEX (status, id)  ← "가장 오래된 pending" 조회용
```

## 5. 측정 결과

`docker compose up --build`로 띄운 실제 환경(앱 컨테이너 CPU 0.5 / 메모리 512M 제한 적용 확인)에서 측정했습니다.

| 항목 | 결과 |
|---|---|
| `POST /api/jobs` 응답 시간 | **약 0.02초** (파일 생성과 무관하게 즉시 202) |
| 10만 건 엑셀 생성 시간 | **약 10~14초** / 건 |
| 생성 중 컨테이너 메모리 (`docker stats`) | **약 47~52MiB** (한도 512MB의 약 10%) |
| 프로세스 최대 메모리 (ru_maxrss) | 약 67MB |
| 결과 파일 크기 | 약 4.2MB |
| 요청 25건 동시 전송 | 21건 수락(202), 4건 거절(429). 처리 중인 작업은 **항상 1개**, 모두 처리되는 동안 메모리 **49~52MiB로 거의 일정** |
| 생성 중 목록 조회 API 응답 | 평소 0.03초 → 생성 중 0.12~0.25초 (아래 "한계" 참고) |
| 생성 도중 컨테이너 강제 종료(`docker kill`) | 재시작 시 해당 job `failed` 처리, 남은 임시 파일 자동 삭제, 이후 요청 정상 처리 |

### 테스트하다 발견해서 고친 문제
처음엔 강제 종료 후에도 `.part` 파일만 지우면 된다고 생각했는데, 실제로 확인해 보니 `.part` 파일은 없고 **컨테이너 `/tmp`에 25MB짜리 파일**이 남아 있었습니다.
XlsxWriter의 `constant_memory` 모드는 메모리 대신 **임시 파일에 행 데이터를 먼저 쓰고, 마지막 `close()` 때 압축해서 .xlsx를 만드는** 방식이기 때문입니다. (압축 전 25MB → 압축 후 4.2MB)
그래서 임시 파일 위치를 `EXPORT_DIR/tmp`로 고정하고, 서버 시작 시 이 폴더와 `.part` 파일을 비우도록 했습니다. (`worker.py: cleanup_leftover_files`)
→ "메모리를 아끼는 대신 디스크를 쓴다"는 트레이드오프를 직접 확인한 사례입니다.

## 6. 한계와 개선 방향

| 한계 | 개선 방향 |
|---|---|
| 요청마다 DB 연결을 새로 엶 | `psycopg_pool`로 커넥션 풀 사용 |
| 폴링은 변화가 없어도 요청을 보냄 | SSE로 서버가 상태 변화를 밀어주기 |
| 만든 파일이 계속 쌓임 | 생성 후 N일 지난 파일과 job을 정리하는 작업 추가 |
| 대기열 상한 체크(count 후 insert)가 원자적이지 않아 동시 요청 시 20개를 살짝 넘을 수 있음 | 허용 가능한 수준이라 두었음. 엄격히 하려면 advisory lock 사용 |
| 엑셀 생성(CPU 작업)과 API가 같은 프로세스라 생성 중에는 API 응답이 조금 느려짐 (GIL) | 워커를 별도 프로세스로 분리. 단, 메모리가 늘어나므로 제약 안에서 트레이드오프 |
| 같은 데이터를 요청해도 매번 새로 만듦 | 데이터가 바뀌지 않았다면 직전 파일 재사용 (캐싱) |
| 필터(기간, 카테고리 등) 없음 | `POST /api/jobs`에 조건을 받아 job에 저장 |

## 7. 프로젝트 구조

```
.
├── docker-compose.yml
├── db/init/
│   ├── 01_schema.sql      # orders, jobs 테이블
│   └── 02_seed.sql        # 더미 주문 10만 건 (generate_series)
└── app/
    ├── Dockerfile
    ├── main.py            # API + 서버 시작/종료 시 워커 관리

    ├── db.py              # DB 연결
    └── static/index.html  # 데이터 요청 목록 화면
```
